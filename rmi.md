- Use namespace bdg::bison::rmi and put the code inside the folder src\rmi. The code from the server is in the subfolder src\rmi\server and the client code is in src\rmi\client. The shared code is in src\rmi\shared.
- The framework should be platform independent, so any functionality that depends on the platform (Windows, Linux, Mac) should be abstracted into a class and implemented in the platform subfolder. The cmakefile for each of the target platforms should only include the code from their corresponding platform (for example, platform\linux for linux), as well as all the code that is not platform dependent. That way, we can have the platform independency without having to use interfaces with virtual methods
- The purpose is creating a RMI (Remote Method Invocation) system using the bison library for creating remote objects on a server and using them from a client as if they were local objects
- The rmi framework uses the bison library for managing the remote objects and serializing and deserializing the information sent over the transport
- Use a server / client architecture, similar to the one used in Apache Thrift. The framework is modular and separates the business logic from the transport layer, allowing for different transport protocols (e.g., TCP, HTTP, pipes, in-memory stream).
- The client class has the following interface:
  - constructor(transport&&): Creates the client using the specified transport layer
  - connect(bison::dynamic&& params): Connects to the server using the given params. Those params are also passed to the transport layer for its initialization (for example, the ip and port to connect to). The client uses a worker thread for handling the connection to the server
  - bison::dynamic describe(std::string name): if no name is given, return a list of all the classes registered in the server. If a name is given, returns the fields of that class, so the client can know their structure
  - bison::remote::dynamic instantiate(klass, bison::dynamic&& params): Creates an instance of the given bison class on the server. The supported classes must be registered in the server using bison addClass. For privacy and security, each connection in the server has a separate context for each client and the client only has access to their instanced objects. When instantiated, the function return a wrapper object for the server side object. That bison::remote::dynamic has the same interface as bison::dynamic, but makes the calls through the client object to the server:
      - clear(): removes the fields that were set in the remote object, reverting it to their default values through the inheritance system in bison
      - set(bison::dynamic&& fields): sets the given fields in the remote object. It doesnt clear the fields that were not specified in the params, just sets the ones included
      - get(bison::dynamic& fields): if fields is empty, fills the fields object with a copy of the remote object. if fields are specified, sets the values of those fields that are set on the remote object. This is similar to how GraphQL works, where you pass a json like structure of the fields that you want to get and the get method returns the same fields objects with the values set
      - std::future<bison::dynamic> call(bison::dynamic&& params, bool oneway): Makes the remote call on the server object and returns a future that can be waited on to get the response. If oneway is true, the client doesn't need a response and the server can omit sending a response, reducing the traffic overhead
      - onEvent(string name, std::func<void(bison::dynamic&& params)>): registers an event handler that can be called from the server. For example, an "onReload" event that gets triggered when the object is reloaded. The events are called from the client thread, so the client has to handle the synchronization
  - destroy(id): releases the object with that id on the server
  - disconnect(): Closes the connection
- The server class has the following interface:
  - constructor(transport&&): Creates the server using the specified transport layer
  - listen(bison::dynamic&& params): Starts the listening thread using the given params and initializes the transport layer with those params. The server creates an instance of the context class to hold all the information for the connected client, including a dictionary of the instanced objects (id, object). The listening thread waits on connections from the transport layer and spawns a separate thread for each connected client that processes the requests from that client. When a client disconnects, the server releases all the objects that were still alive in the context of that client.
  - stop(): Stops the listening thread and closes all the active connections
